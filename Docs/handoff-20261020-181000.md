## 2. 两个最容易再踩的坑（务必先看）

### 2.1 UPM 克隆 git 包**没有重试**，一次网络重置=整次 resolve 作废

本机直连 github 是**间歇性**可用的（`ls-remote` 5 次错 1 次；`curl github.com` 时而 20s 超时）。
17:28 那次 resolve 耗时 **1283592 ms（21.4 分钟）** 后整体失败，而 `upm.log` 里**仍写着**
`project:resolve-packages --> 200`——表面像"没反应"。

**判断"这次到底成了没"要看这两个文件，不要看 upm.log 的 200**：

1. `Library/PackageManager/projectResolution.json` 的 `outputs` 里有没有新包
2. `Packages/packages-lock.json` 的 mtime 有没有变

失败时 upm.log 会留下真实原因（`git ls-remote` / `git fetch` 的 stderr）。
建了本地镜像后，第二次 resolve 只用 **11401 ms**。

### 2.2 `insteadOf` 是前缀匹配，`*` 不是通配符

实测：`insteadOf = https://github.com/a/B.git` + URL `https://github.com/a/B.git?path=sub`
→ 改写成 `/mirror/B.git?path=sub`（查询参数被原样拼接）；写成 `.git*` 则**完全不命中**。

所以**带 `?path=` 的包（LitMotion、UIEffect）不受镜像保护**，仍需真实网络。
它们已在 `Library/PackageCache`，正常不会再克隆；若哪天被删缓存后解析失败，
大概率就是这两条又走了真实网络。
