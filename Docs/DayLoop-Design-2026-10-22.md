# 「有循环的一天」设计方案（草案 v0.1）

- 日期：2026-10-22
- 状态：**草案，待用户确认后才进工程**
- 依据：实机代码，不采信规格书
- 相关：`Docs/DesignAudit-2026-10-22.md`、`Docs/ContentHealthReport.md`

---

## 0. 结论

你的判断是对的，但问题比「加一个每日循环」更基础：

> **现在这游戏里没有「一天」。**

每日行动点给了 12 点，一个阶段只要 6/6/8 次行动，每次行动只花 1 点。玩家一口气做完整个阶段也用不完 12 点，所以 `currentDay` 永远停在第 1 天，睡眠、时段、日期标签全是装饰。

所以本轮不是「加循环」，而是**把两个打架的时钟合成一个**：阶段预算决定「几天」，每天固定几次行动，夜晚强制结算。

## 1. 现状诊断（每条都可在源码复核）

| # | 事实 | 证据 |
| --- | --- | --- |
| D1 | 每日行动点 = 4 时段 × 3 点 = **12 点** | `TimeSystem/TimeActionState.cs:22-24` |
| D2 | 一个阶段只有 **6 / 6 / 8** 点预算，每次活动扣 1 点 | `MvpSampleDataFactory.cs:50-52`、`StageController.cs:105-110` |
| D3 | 行动同时扣「每日行动点」和「阶段预算」，两个时钟并行 | `Flow/LocationActionExecutor.cs:163`、`StageController.cs:106` |
| D4 | **精力从不被消耗**：训练/小游戏/事件都没有精力代价，只有休息 +8 | `MvpSampleDataFactory.cs:325-421` |
| D5 | **压力在白天不增长**：唯一来源是 Boss 失败奖励 | `ContentHealthReport.md` 第 5 节 |
| D6 | 睡眠只在玩家主动交互时触发；`DayStarted` 仅在夜晚睡时 +1 天 | `TimeActionController.cs:94-124` |
| D7 | 结果：一次不睡就能打完阶段，日期、时段、日夜全部不参与决策 | D1+D2+D3 推论 |

**一句话**：三个资源（阶段时间、精力、压力）里只有一个真正起作用，另外两个是显示用的数字。所以玩家没有「怎么安排今天」的问题可回答。

## 2. 设计目标

| 编号 | 目标 | 可验收的表现 |
| --- | --- | --- |
| DAY-001 | 每天行动次数固定且有限 | 一天最多 3 次行动，第 4 次提示「今天做不了了，回去睡觉」 |
| DAY-002 | 阶段按天推进，不按次数推进 | HUD 显示「第 X 天 / 共 N 天」，阶段 1 为 2 天、阶段 3 为 3 天 |
| DAY-003 | 学习有代价，休息有收益 | 连续学习会被精力挡住，必须至少穿插 1 次休息 |
| DAY-004 | 夜晚是结算点，不是又一段时间 | 夜晚只能睡觉 / 免费交互（门、背包、传送） |
| DAY-005 | 每天不完全一样（第二期） | 早晨有概率触发「今日事件」，改变当天规则 |

## 3. 一天的形状

### 3.1 时段与行动格

| 时段 | 行动格 | 可做什么 | 说明 |
| --- | ---: | --- | --- |
| 早晨 | 1 | 活动 / 地图交互 | 学习类可用 |
| 下午 | 1 | 活动 / 地图交互 | 学习类可用 |
| 傍晚 | 1 | 活动 / 地图交互 | 学习类可用 |
| 夜晚 | 0 | 只能睡觉、背包、传送门 | 强制结算 |

> 关键改动：夜晚不再是第 4 个行动时段，而是「结算 + 下一段开始」的边界。现有 `TimeActionState` 的 4 时段结构保留，只把每时段点数从 3 改成 1，Night 不计入可用行动。

### 3.2 状态机

```text
阶段开始
  ↓
第 X 天 · 早晨（行动 1/3）
  ↓ 行动
下午（2/3） → 傍晚（3/3）
  ↓ 行动格用尽
夜晚：强制结算（睡眠）→ 第 X+1 天早晨
  ↓ 最后一天的最后一次行动
Boss 挑战 → 下一阶段
```

### 3.3 天数换算（不改现有阶段预算）

| 阶段 | 现有预算 | 天数 = ceil(预算 / 3) | 每天行动分布 |
| --- | ---: | ---: | --- |
| 适应新学期 | 6 | 2 天 | 3 + 3 |
| 月考压力 | 6 | 2 天 | 3 + 3 |
| 期末冲刺 | 8 | 3 天 | 3 + 3 + 2 |

> 这样改的好处：`timeLimit`、Boss 进度、结局阈值全部不用动，只改「行动怎么分配到天」。

## 4. 资源三角（本次的核心）

### 4.1 提议数值

| 行为 | 精力 | 压力 | 其他 |
| --- | ---: | ---: | --- |
| 学习类活动（训练 / 小游戏 / 课堂） | **−12** | **+3** | 主属性 +3~4（不变） |
| 休息类活动（睡觉 / 听音乐 / 散步） | +8 | −4 | 精力上限 +2（不变） |
| 夜晚睡眠（强制） | +15 | −2 | 公交站睡：心情 −5（已有） |
| 精力门槛 | 学习类需要精力 ≥ 12，否则按钮置灰并提示 | | |

### 4.2 验算：为什么精力取 12

- 阶段 3 共 8 次行动、跨 3 天，中间有 2 次夜晚睡眠。
- 全部选学习：总消耗 `8 × 12 = 96`，回复 `2 × 15 = 30`，初始精力 60。
- 净额 `60 − 96 + 30 = −6` → **不够，必须至少休息 1 次**（休息 +8 刚好补上缺口）。
- 若精力代价取 10：`60 − 80 + 30 = +10` → 全程学习也够，**约束失效**。
- 若取 14：`60 − 112 + 30 = −22` → 要休息 3 次，8 次行动里只剩 5 次成长，**过严**。

| 精力代价 | 8 次全学习净额 | 是否逼出休息 | 判定 |
| ---: | ---: | --- | --- |
| 10 | +10 | 否 | 无效 |
| **12** | **−6** | **是（≥1 次）** | **采用** |
| 14 | −22 | 是（≥3 次） | 过严 |

### 4.3 压力曲线验算

- 8 次学习：`8 × 3 = +24`；2 次睡眠：`−4`；净 `+20`；初始 20 → **40**。
- 若阶段 1（6 次学习、1 次睡眠）：`18 − 2 = +16` → 20 → **36**。
- 建议阈值：**压力 ≥ 40 时，学习类收益 −25%；≥ 70 时，每天只能行动 2 次**。
  - 阶段 3 全学习路线正好压到 40，触发第一档惩罚但不致命 —— 这是有意设计的「临界感」。

## 5. 每日事件（第二期，DAY-005）

- 触发：每天早晨 50% 概率，从 6 个事件池抽 1 个；不触发时显示「今天没什么特别的」。
- 形式：三选一或直接生效，只影响**当天**。
- 示例池（够用即可，不追求数量）：

| 事件 | 效果 |
| --- | --- |
| 下雨 | 公园类活动收益 −1，图书馆类 +1 |
| 家里有事 | 傍晚必须回家（否则心情 −5） |
| 老师加课 | 今天学校活动精力消耗 −4 |
| 同学约球 | 新增一次性活动「打球」：精力 −10、社交 +5、压力 −6 |
| 停电 | 电脑类活动不可用 |
| 考试临近 | 今天学习类压力 +2 |

> 事件只改当天规则，不写进存档的长期状态，避免存档结构复杂化。

## 6. 与现有系统的接线点

| 改动 | 文件 | 具体做法 |
| --- | --- | --- |
| 每天 3 格 | `TimeSystem/TimeActionState.cs` | `ActionPointsPerPeriod` 3→1；`RemainingDailyActionPoints` 排除 Night |
| 强制入夜 | `TimeSystem/TimeActionController.cs` | 行动格用尽 → `RequiresSleep = true`，活动入口给提示 |

| 天数与 Boss | `StageController.cs` | 预算归零即最后一天结束，逻辑不变；只补「第 N 天」显示 |
| HUD | `UI/Map/TimeActionHudView.cs` | 显示「第 X 天 / 共 N 天 · 今天还剩 M 次」；`dateMilestones` 改按天 |

| 期 | 内容 | 验收标准 | 预估 |
| --- | --- | --- | --- |
| P0 | 每天 3 格 + 强制入夜 + 睡眠结算 + 精力代价/门槛 | 阶段 1 只能做 2 天；第 3 次行动后提示回去睡觉；精力不足时学习被挡住 | 1 个工作段 |

| P3 | 时段差异（早/午/晚收益修正） | 同一活动在不同时段数值不同 | 可选，最后做 |

## 8. 风险与必须重跑的东西

1. **结局阈值会变**：压力来源从「只有 Boss 失败」变成「每次学习 +3」，`ending_pressure_recovery` 的 30 点门槛会变得容易。改完必须重跑 `Tools/Student Growth/Content/运行内容体检`，按新上界重标定。
2. **存档兼容**：`ActivityData` 新增字段默认 0，旧资产按 0 处理即可；但已存档的 `TimeActionState.currentActionPoints` 上限变了（3→1），读档时要 `Normalize()` 夹紧。
3. **Boss 节奏**：阶段 1 从 6 次行动压成 2 天，玩家可能觉得短；这是内容量问题，不是循环问题，先不做补偿。
4. **不要动 `timeCost` 的语义**：它同时用于扣阶段预算，改成「精力代价」会连带打乱 Boss 节奏。精力和精力代价必须是新字段。

## 9. 待确认（不超过 3 个）

1. **一天几次行动**？我建议 3 次（早/午/晚），阶段 1 就是 2 天、阶段 3 是 3 天。要更长就变成 4 次/天，但阶段预算也得跟着加。
2. **强度按哪档**？我建议「精力 −12 / 压力 +3 / 睡眠 +15、−2」，理由见 4.2 的验算。想更硬可以把睡眠回复降到 +10。
3. **允许熬夜吗**？现在夜晚是强制结算。如果要留「熬夜学习」的口子，就得定义代价（次日精力上限 −20、压力 +6），这会让循环更真实，但实现多一层。

### 「觉得少」的两种解法（供下次决策）

| 解法 | 做法 | 代价 |
| --- | --- | --- |
| A. 加免费行动（推荐） | 购物、背包、和 NPC 说话、看地图**不占格**；每天再固定 1 次免费闲聊 | 0 数值改动，只改「什么算行动」 |
| B. 加总行动量 | 阶段预算 6/6/8 → 9/9/12，仍 3 格/天（阶段变 3/3/4 天） | 要重跑内容体检与结局阈值；内容供给 14 个活动仍够，但重复度上升 |
